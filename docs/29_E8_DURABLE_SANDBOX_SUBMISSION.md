# E8 durable sandbox submission boundary

An additive PostgreSQL migration creates `archon_sandbox_submissions`, separate from canonical geometry, versions, ChangeSets and their approval tables. It stores run ID, manifest digest, an opaque approval reference, lifecycle state, actual provider workitem ID and safe diagnostics. Credentials, signed URLs, DWG bytes and client drawing contents are excluded.

An INSERT with the run primary key atomically permits one claim across processes. A guarded UPDATE permits one CLAIMED → SUBMITTING transition. There is no expiry, reclaim, deletion or retry API. A crash after this transition leaves SUBMITTING, permanently blocking automatic resubmission. A known provider ID is recorded as SUBMITTED; an ambiguous network or persistence result becomes UNKNOWN when the database is available. If that acknowledgement fails too, the existing SUBMITTING claim still blocks retries. Unique provider IDs reject cross-run association. These states do not claim APS job success or ARCHON approval.

`submitReviewedSandbox` is a private, disabled-by-default server boundary. It rebuilds and hashes the fixed synthetic test manifest, requires a matching explicit server-issued approval reference and deadline, runs trusted live preflight, rechecks expiry, durably claims the run and begins submission before one provider invocation. Timeout, malformed provider ID and persistence acknowledgement failure never trigger retry. Frozen snapshots prevent mutation of the review or grant while preflight awaits.

The ledger is not itself an authorization store. An approval object, preflight callback and submission transport must come from a trusted server operator boundary; callers must not expose this helper as a public request that accepts caller-supplied evidence. There is deliberately no enabled runtime caller or HTTP execution route in this checkpoint. Live resource/version/digest rechecks, seed/input readback, output absence, private capability binding, APS submission/polling and result reconciliation still need wiring. No execution approval is requested until that wiring is ready.

Validation: real disposable PostgreSQL integration tests cover thirty concurrent claims, distinct clients, crash-like SUBMITTING state, UNKNOWN blocking, terminal transitions and duplicate provider IDs. Guard tests cover disabled execution, absent/mismatched/expired approvals, manifest edits, preflight binding, timeout and failed database acknowledgement.

Geometric/dimensional validation is confined to the fixed seven-entity fixture. Native saved-DWG reopening, project material/design/rules and actual reconciliation remain pending approved execution. This migration does not alter an approved Building Graph and creates no production ChangeSet.
